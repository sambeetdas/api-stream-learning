How does the server tell the browser "something new happened"?

← Back to the demo

The problem

Normal HTTP works like a phone call where only the browser can dial: the browser asks, the server answers, and the call ends. The server cannot start a conversation. But many apps need exactly that: a new chat message, a price change, a finished job.

This demo shows five ways to solve it. They all deliver the same messages from the same SQLite database, so you can compare them side by side.

TechniqueOne-line ideaEndpoint here
Short pollingAsk again and again on a timer.GET /messages?after=ID
Long pollingAsk, and the server waits to answer until there is news.GET /longpoll?after=ID
Server-Sent EventsKeep one response open; the server keeps writing to it.GET /stream
HTTP streamingSame idea, but plain JSON lines and no special protocol.GET /stream/ndjson?after=ID
WebSocketUpgrade to a two-way connection.GET /ws?after=ID

Sending a message is a normal POST /messages for every technique except WebSocket, which sends over its own connection.

Each technique has an Architecture & system design box. For how it all fits into a real system with many servers, see The bigger picture.

1. Short polling

The simplest idea. The page asks "anything new since message 7?" every few seconds. The server answers right away, even if the answer is "no".

Browser                         Server
   | GET /messages?after=7  --->  |
   | <--- []   (nothing new)     |
   |        ... 2 seconds ...     |
   | GET /messages?after=7  --->  |
   | <--- [{id:8, ...}]          |

Good

  • Trivial to build and debug; it is just normal requests.
  • Works everywhere: proxies, old browsers, serverless.
  • Server holds no connections open.

Not so good

  • Delay: up to the full polling interval (2s here).
  • Wasteful: most requests return nothing, but still pay for headers.
  • Faster polling means lower delay but more load.

Architecture & system design

  • Server state: none. Each poll is an independent request, so any server instance can answer it. Round-robin load balancing, autoscaling and serverless functions all work with no changes.
  • Load grows with clients, not with messages: 10,000 clients polling every 2s is 5,000 requests per second even when nothing happens, and each one usually touches the database. That idle load is the real cost.
  • Making it cheaper: put a cache (e.g. Redis) in front of the database, return 304 Not Modified with ETags, or let a CDN cache the answer for a second or two when every client sees the same data.
  • Many servers: no extra pieces needed. The database is the single source of truth and the after= cursor means every poll just asks it "what is newer than X?".
  • Reliability: naturally strong. The client drives everything with its cursor, so nothing is lost as long as the data is still stored.
  • Mobile: waking the radio every few seconds drains battery and data, so mobile apps poll slowly or use push notifications instead.

Use cases

  • Dashboards that refresh every 30-60 seconds.
  • Checking the status of a background job ("is my export ready?").
  • Anything where a few seconds of delay is fine and simplicity matters most.

Code

// browser
setInterval(() => {
  $.getJSON('/messages', { after: lastId }, msgs => msgs.forEach(show));
}, 2000);

// server (MessagesController)
[HttpGet]
public List<Message> Get([FromQuery] long after = 0) => store.GetAfter(after);

Watch in the demo: "HTTP requests made" climbs every 2 seconds even when nobody sends anything.

2. Long polling

A smarter version of polling. The page asks "anything new since message 7?" and the server does not answer yet if there is nothing. It holds the request open and answers the moment a message arrives (or after about 25 seconds, so the connection does not die of old age). The page then immediately asks again. 

Browser                         Server
   | GET /longpoll?after=7  --->  |
   |        ... waiting ...       |   (request stays open)
   |                              |   <- someone posts message 8
   | <--- [{id:8, ...}]          |
   | GET /longpoll?after=8  --->  |   (ask again right away)

Good

  • Near-instant delivery, with far fewer empty requests than polling.
  • Still just plain HTTP, so it passes almost any proxy or firewall.

Not so good

  • A new request (with headers) after every message: costly if messages are frequent.
  • Messages that arrive between two requests must be caught up (that is what after= is for).
  • Each waiting client occupies a request on the server.

Architecture & system design

  • Server state: one waiting request per client. The server must use asynchronous I/O (ASP.NET Core does) so waiting requests do not each tie up a thread; thread-per-request servers run out of threads quickly.
  • Many servers: the request is waiting on server A, but the new message may be posted to server B. Servers therefore need a shared backplane (Redis pub/sub, Azure Service Bus, PostgreSQL LISTEN/NOTIFY) to tell each other "something new happened". Sticky sessions are not needed: every request is independent and the cursor resumes anywhere.
  • Timeouts: every hop (load balancer, reverse proxy, corporate proxy) closes idle requests, often after about 60 seconds. The hold time must stay below the smallest one; this demo uses 25 seconds.
  • Thundering herd: one broadcast message answers every waiting client at once, and they all send their next request at the same moment. At scale this creates load spikes; adding a little random delay (jitter) spreads them out.
  • Cost per message: each delivery is a full HTTP request and response, including authentication and logging, so busy feeds cost much more than with a stream.
  • Serverless: a poor fit. You pay for time spent waiting and hit execution time limits.

Use cases

  • Notifications and chat when WebSockets are blocked or unavailable (a classic fallback).
  • Low-to-medium traffic apps that need "instant" updates without special infrastructure.

Code

// browser
function ask() {
  $.getJSON('/longpoll', { after: lastId }, msgs => { msgs.forEach(show); ask(); });
}
ask();

// server (MessageFeed.WaitForAfter)
var existing = store.GetAfter(afterId);
if (existing.Count > 0) return existing;          // news already waiting
await subscription.Reader.ReadAsync(timeoutToken); // otherwise wait for a message
return store.GetAfter(afterId);

Watch in the demo: "HTTP requests made" only grows when a message arrives. The "Connection Open" column on the server shows the held-open requests.

3. Server-Sent Events (SSE)

The browser makes one request and the server never finishes the response. It just keeps writing small text events to it as things happen. The browser has a built-in EventSource that reads these events, reconnects automatically if the connection drops, and tells the server the last event id it saw (Last-Event-ID) so the server can fill in what was missed. 

HTTP/1.1 200 OK
Content-Type: text/event-stream

id: 8
event: message
data: {"id":8,"text":"hello"}

: ping                  <- comment, used as keep-alive

id: 9
event: message
data: {"id":9,"text":"world"}

Each event ends with a blank line. That is the whole format.

Good

  • Very simple on both sides; the browser does the hard work.
  • Automatic reconnect and resume.
  • Plain HTTP, so it works with normal auth, logging and proxies.

Not so good

  • One direction only: server to client.
  • EventSource cannot set custom headers (auth tokens need cookies or a query string).
  • Text only (no binary).
  • Over HTTP/1.1 browsers allow only about 6 connections per site, shared across tabs. HTTP/2 removes this limit.

Architecture & system design

  • Server state: one open connection per client, costing a socket and some memory for as long as the user stays. Async servers like Kestrel can hold many thousands per instance, but measure your own limit and set one (e.g. Kestrel's MaxConcurrentConnections).
  • Many servers: each server only knows its own connections, so a message posted on server B must reach clients connected to server A through a backplane (Redis pub/sub, a message broker). This demo's in-memory Broadcaster only works on a single server; it is the piece you would replace to scale out.
  • No sticky sessions needed: if events are stored durably and have ids, a reconnecting client can land on any server and resume from Last-Event-ID.
  • Infrastructure: proxies must not buffer the response (this demo sends X-Accel-Buffering: no; response compression can also buffer), and heartbeats must be more frequent than the shortest idle timeout on the path. Serve it over HTTP/2 so many streams share one connection and the 6-connection browser limit disappears.
  • Deployments: restarting a server drops all its connections at once and every client reconnects together (a reconnect storm). Use graceful shutdown, and spread reconnects with the retry: field and random backoff.
  • Security: a connection can outlive the token that opened it, so decide what happens on expiry (close it and let the client reconnect with a fresh token). Avoid tokens in the URL where you can, because URLs end up in access logs.
  • Reliability: event ids plus a stored history give at-least-once delivery; the client ignores ids it has already seen (as app.js does), which makes it effectively exactly-once.

Use cases

  • Live feeds, notifications, stock or sports tickers.
  • Progress of a long task (uploads, builds, deployments).
  • Streaming AI chat responses token by token.

Code

// browser
const es = new EventSource('/stream');
es.addEventListener('message', e => show(JSON.parse(e.data)));

// server (SseStreamController)
Response.Headers.ContentType = "text/event-stream";
await foreach (var m in feed.Stream(lastId, heartbeat, ct))
{
    await Response.WriteAsync($"id: {m.Id}\nevent: message\ndata: {json}\n\n", ct);
    await Response.Body.FlushAsync(ct);   // without Flush the event sits in a buffer
}

Watch in the demo: just one request, however many messages arrive. Stop the server and restart it: the page reconnects on its own and resumes without gaps.

4. HTTP streaming (NDJSON)

The same trick as SSE, with no special protocol on top. The server keeps one response open and writes one JSON object per line (NDJSON, "newline-delimited JSON"). The page reads the body piece by piece with fetch and splits it into lines. Because there is no EventSource to help, the page has to handle reconnecting and resuming itself (it passes ?after=). 

HTTP/1.1 200 OK
Content-Type: application/x-ndjson
Transfer-Encoding: chunked

{"id":8,"text":"hello"}
{"id":9,"text":"world"}
                                <- empty line = heartbeat
{"id":10,"text":"again"}

Good

  • Works from any HTTP client: browsers, curl, mobile apps, backend services.
  • You control the headers (auth tokens work), unlike EventSource.
  • Easy to stream large results without loading everything in memory.

Not so good

  • No automatic reconnect or resume: you write it.
  • Some proxies buffer responses and break the "live" feel.
  • One direction only, like SSE.

Architecture & system design

  • Same server model as SSE: one long-lived response per client, so the same points apply: memory per connection, a backplane to scale out, no proxy buffering, heartbeats below idle timeouts.
  • Your protocol, your rules: nothing is standard beyond "one JSON object per line". You design the resume cursor (?after= here), error messages inside the stream and versioning, and every client has to implement them.
  • Backpressure: if a client reads slowly, TCP slows the server's writes down and messages queue up on the server. Limit that queue per client: drop, merge, or disconnect slow readers. This demo uses an unbounded queue, which is fine for learning but a memory risk in production. The same applies to SSE and WebSocket.
  • Large results: streaming rows as they are read (IAsyncEnumerable in ASP.NET Core) keeps server memory flat no matter how big an export is, and the client can start using data straight away.
  • Between your own services: gRPC server streaming is the typed, more efficient alternative. Plain chunked JSON streams are common in public and infrastructure APIs (for example the Kubernetes "watch" and Docker events APIs) because any HTTP client can read them.

Use cases

  • APIs that return big result sets progressively (exports, search results, log tailing).
  • LLM and AI APIs that stream tokens to your backend or a custom client.
  • Server-to-server and command-line streaming, where EventSource does not exist.

Code

// browser
const res = await fetch('/stream/ndjson?after=' + lastId);
const reader = res.body.getReader();
const decoder = new TextDecoder();
let buffer = '';
while (true) {
  const { done, value } = await reader.read();
  if (done) break;
  buffer += decoder.decode(value, { stream: true });
  const lines = buffer.split('\n');
  buffer = lines.pop();                       // keep the incomplete last line
  lines.filter(Boolean).forEach(l => show(JSON.parse(l)));
}

// server (NdjsonStreamController)
Response.Headers.ContentType = "application/x-ndjson";
await Response.WriteAsync(json + "\n", ct);
await Response.Body.FlushAsync(ct);

Watch in the demo: "Body bytes received" counts the raw bytes of the stream, including the heartbeat lines. Try it in a terminal: curl.exe -N http://localhost:5099/stream/ndjson

5. WebSocket

The browser starts with a normal HTTP request that says "let's switch protocols". If the server agrees (101 Switching Protocols), the connection stops being HTTP and becomes a persistent, two-way pipe. Either side can send a message at any moment. In this demo, when WebSocket is selected, the page even sends your typed message up the socket instead of using POST. 

Browser                              Server
   | GET /ws  (Upgrade: websocket) --> |
   | <-- 101 Switching Protocols ----- |
   |                                    |
   | <==== {id:8,...} ================== |   server pushes
   | ==== {"text":"hi"} ==============> |   client sends on the same connection

Good

  • True two-way, low-latency communication.
  • Small overhead per message once connected.
  • Supports text and binary.

Not so good

  • No automatic reconnect or resume: you write it.
  • Not plain HTTP afterwards, so some proxies and load balancers need configuration.
  • Harder to scale and secure; you manage connection state yourself.

Architecture & system design

  • Server state: one stateful, two-way connection per client, with buffers in both directions. You also need an application protocol on top: message types, acknowledgements, errors and versioning. Libraries such as SignalR, Socket.IO, or MQTT and STOMP over WebSocket provide one.
  • Many servers: like SSE, a backplane is needed so a message reaches clients connected to other servers. Load balancers must support the Upgrade handshake. Raw WebSockets do not need sticky sessions (the connection lives on one server), but frameworks that negotiate first, such as SignalR on several servers, need them unless you use WebSockets only or a managed service.
  • Lost HTTP features: after the handshake it is no longer HTTP. Per-request logging, caching, HTTP rate limiting and many WAF rules no longer see individual messages, so you add your own per-message validation, rate limiting and logging. Some corporate networks block WebSockets entirely, which is why fallbacks exist.
  • Security: browsers do not apply CORS to WebSockets. Check the Origin header on the handshake (to prevent cross-site WebSocket hijacking), authenticate at connect time, and authorize every incoming message, not only the connection.
  • Operations: plan for connection draining on deploys, reconnect storms, ping/pong heartbeats, and monitoring of open connections and per-connection memory.
  • Managed services: Azure Web PubSub, Azure SignalR Service, AWS API Gateway WebSockets and providers such as Pusher or Ably hold the connections for you, so your servers stay stateless.

Use cases

  • Chat apps and collaborative editing.
  • Multiplayer games and live cursors.
  • Trading screens and anything where the client sends frequent small messages too.

Code

// browser
const ws = new WebSocket('ws://' + location.host + '/ws?after=' + lastId);
ws.onmessage = e => show(JSON.parse(e.data));
ws.send(JSON.stringify({ text: 'hello' }));   // client to server

// server (WebSocketController)
using var socket = await HttpContext.WebSockets.AcceptWebSocketAsync();
await socket.SendAsync(bytes, WebSocketMessageType.Text, true, ct);  // server to client
var result = await socket.ReceiveAsync(buffer, ct);                   // client to server

Watch in the demo: the "Connected (two-way)" state, and that only the handshake counts as an HTTP request.

The bigger picture: system design

The transport is only the last step. In a real system, a "live update" travels through several parts, and most of the hard problems (scale, reliability, security) live in those parts, not in the choice between SSE and WebSocket. 

        Clients (browsers, mobile apps, other services)
                 |  HTTPS / WSS
        +--------v---------+
        |  Load balancer / |   idle timeouts, Upgrade support,
        |  reverse proxy   |   response buffering, TLS
        +---+----------+---+
            |          |
     +------v---+  +---v------+
     | App      |  | App      |   hold the open connections,
     | server 1 |  | server 2 |   check who may see what
     +--+----^--+  +--+----^--+
        |    |        |    |
        |  +-+--------+----+-------------+
        |  |  Backplane / pub-sub        |   "message 42 exists" reaches
        |  |  (Redis, Service Bus, Kafka)|   every server
        |  +-----------------------------+
        |
     +--v-----------------+
     | Database / log     |   source of truth; clients replay from
     | (SQLite here)      |   their last id after a reconnect
     +--------------------+

This demo squeezes all of this into one process: MessageStore is the database, and the in-memory Broadcaster plays the backplane. That is why it only works on a single server.

1. Separate the write path from the push path

Saving a message (POST /messages) and pushing it to clients are two different jobs. Write to the database first, then publish an event saying it exists. If the publish can fail after the write succeeded (or the other way round), use the transactional outbox pattern: store the event in the same database transaction and publish it from there, so the two never disagree.

2. Push is best effort; the stored log makes it reliable

  • Connections drop all the time (Wi-Fi changes, laptops sleep, deploys). Never rely on "the client was connected when it happened".
  • Give every event an increasing id and keep a history. Clients remember their last id and ask for everything after it when they reconnect (after= and Last-Event-ID here).
  • This gives at-least-once delivery. Clients ignore ids they have already seen, so it behaves as exactly-once.
  • Mind the gap between "replay history" and "go live": this demo subscribes before reading history and drops duplicates, so no message can slip through between the two (see MessageFeed.Stream).
  • Ordering is easy with one sequence (like here). With many partitions or shards, order is usually guaranteed only within one partition.

3. Open connections are a resource to plan for

  • Each connection costs memory, a socket, and capacity on every load balancer and proxy in the path. Managed services usually price by concurrent connections.
  • Plan capacity on peak concurrent users, not requests per second. Load test with realistic connection counts and idle periods.
  • Set limits, and decide what happens when they are reached: refuse new connections, or fall back to polling.

4. Slow consumers and backpressure

A client on a bad network reads slowly while messages keep coming. Without a limit, its queue on the server grows until memory runs out. Use bounded queues per client and pick a policy: drop the oldest messages, merge updates (send only the latest state, e.g. the current price, not every tick), or disconnect the client and let it resume from its last id.

5. Timeouts and heartbeats along the whole path

Every hop between browser and server (corporate proxy, CDN, load balancer, reverse proxy, the server itself) closes connections that look idle, often after about 60 seconds. Send heartbeats more often than the shortest timeout (15 seconds here), and keep long-poll hold times below it (25 seconds here).

6. Deployments and failures

  • A restart drops every connection on that server, and all those clients reconnect at the same moment.
  • Use graceful shutdown (stop accepting, let streams end cleanly), reconnect with random backoff (jitter), and make sure resuming from the last id is cheap for the database.

7. Security

  • Authenticate when the connection opens, and decide what happens when the token expires during a long-lived connection.
  • Authorize fan-out: when one event goes to many clients, check that each receiver may see it (users, groups, channels, tenants).
  • Rate-limit incoming messages (WebSocket) and new connections. Check Origin on WebSocket handshakes.

8. Observability

Track the same kind of numbers this demo shows, in production: open connections, messages delivered per second, delivery delay, reconnect rate, and per-client queue length. A sudden jump in reconnects is often the first sign of a broken proxy or a bad deploy.

9. Build or buy

  • ASP.NET Core SignalR wraps everything on this page: it picks the best transport automatically (WebSocket, then SSE, then long polling), and adds groups, reconnection and a Redis backplane.
  • Azure SignalR Service / Azure Web PubSub (or AWS API Gateway WebSockets, Pusher, Ably) hold the connections for you, so your servers stay stateless and simple to scale.
  • Building it yourself, as in this demo, is the best way to understand it. In production, most teams use a library or managed service and spend their effort on the data and security rules instead.

Questions to ask before choosing

  1. Who sends: only the server, or both sides?
  2. How often do updates happen, and how fast must they arrive?
  3. How many clients are connected at the same time, at peak?
  4. What is between the client and the server (corporate proxies, CDN, serverless platform)?
  5. Who are the clients: browsers, mobile apps, or other services?
  6. What happens if a client misses a message? Is a history to replay from needed?

Which one should I pick?

  • Updates every minute or so, or you just need it working: short polling.
  • Need instant updates and must work behind strict networks: long polling.
  • The server pushes updates to the browser (the most common case): SSE. It is the best default.
  • Streaming to non-browser clients, or you need custom headers: HTTP streaming (NDJSON).
  • The client and server both send often (chat, games, collaboration): WebSocket.
  • Many servers, or you do not want to manage connections at all: SignalR with a backplane, or a managed service such as Azure SignalR Service or Azure Web PubSub.

How to read the stats on the demo page

  • HTTP requests made: the cost of the technique in requests. Compare short polling (grows constantly) with SSE (stays at 1).
  • Reconnects / errors: how often the connection broke. Stop and restart the server to see it go up.
  • Last / average delivery delay: time between the server stamping a message and your page receiving it. With short polling, expect up to 2000 ms; the others should be a few milliseconds. (It compares two clocks, so it is only accurate when browser and server are on the same machine or in sync.)
  • Body bytes received: only the response bodies. HTTP headers, which polling repeats on every request, are not counted, so polling is in reality more expensive than this number shows.
  • Reset button: deletes every message from the database and zeroes the server statistics, so you can start a fresh comparison. Every open tab notices within about 2 seconds and starts fresh too (empty list, client numbers back to zero). Message ids keep counting up afterwards rather than restarting at 1.
  • Server panel (all tabs and clients together):
    • Connection Open: connections open at this moment. Streams and WebSockets show 1 per tab; long polling shows the request being held; short polling is almost always 0 because each request is answered instantly.
    • HTTP Requests: requests received since the server started or the last Reset. Short polling adds one every 2 seconds per tab; SSE, HTTP streaming and WebSocket add one only when they connect or reconnect.
    • Messages Delivered: messages pushed out, counted once per receiving client. Two tabs plus one new message gives 2. Replayed history counts too.
